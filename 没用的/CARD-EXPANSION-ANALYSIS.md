# 卡片库实现现状与扩展压力分析

> 结论先行：**数据层和 UI 层几乎是全自动的，加卡很便宜；真正贵的是"效果实现"和"AI 会用"这两层——每张效果卡都是一段手写的命令式代码，无法批量生成。** 当前架构按"系列"批量加卡（一次 15~25 张）非常顺畅；但"扩展到全部卡片（现役卡池约 1.2 万+ 张）"在现有架构下不可行，需要先做架构改造。详细论证如下。

---

## 1. 现在的卡片库是怎么实现的

卡片分三层加载，全部是**纯手写数据 + 纯手写效果代码**，没有外部数据库、没有脚本系统：

### 1.1 数据层（卡是什么）

| 文件 | 内容 | 加载方式 |
|---|---|---|
| `src/cards.js` | V1 经典 35 张 + 2 套初始卡组 | 定义 `DuelData.CARDS`（全局注册表）、`CARD_LIST`（有序列表）、`DECKS` |
| `src/expansion-cards.js` | 8 个系列约 160 张（HERO/黑羽/废品/希望皇/机壳/艾克佐迪亚/电子龙/水晶机巧）+ 8 套预设卡组 | 往 `CARDS`/`CARD_LIST` 追加，`expansionLoaded` 防重复加载 |
| `src/link-cards.js` | 珠泪 + Link 系列 41 张 + 珠泪卡组 | 同上，重复 id 直接 `throw` |

每张卡就是一行工厂函数调用，例如（`src/expansion-cards.js:10-16`）：

```js
M('cyber-dragon','电子龙','Cyber Dragon',5,2100,1600,'光','机械族','cyber','<效果描述文本>');
S('raigeki'……)  // 魔法    T(...)  // 陷阱
F(...)  // 融合（带素材规格）  Y(...)  // 同调  X(...)  // 超量  P(...)  // 灵摆  L(...)  // 连接
```

- 融合/同调/超量/连接的**素材条件是数据**（`fusion:[{family:'cyber'}]`、`synchro:{minTuners:1}`、`link:{min:2,differentNames:true}` 等），引擎的 `fusionCombos`/`synchroValid`/`linkValid` 通用校验，**这部分加卡不需要碰引擎**。
- `family` 字段决定工坊筛选分组（`D.families`，`src/expansion-cards.js:244`）；`officialName` 必须与 YGOPRODeck 的英文卡名**完全一致**，卡图才能联网自动加载。

### 1.2 效果层（卡会做什么）——手写代码，核心瓶颈

每张效果卡在 `src/effects-*.js`（11 个文件，按系列划分）里用 `E.register / E.trigger / E.spell / E.trap / E.quick` 注册一段**命令式实现**：

```js
// 简单卡：1~3 行（src/effects-classic.js:22）
E.spell('pot-of-greed',{label:'抽2张卡',resolve:(e,c)=>e.draw(c.owner,2),aiScore:1300});

// 复杂卡：触发式效果还要在事件总线里手工接线（src/effects-hero.js:72-101）
E.on('summon',(e,v)=>{ if(v.id==='hero-stratos')e.addTrigger(v.uid,id+'::entry',v); ... });
```

现状统计（实测，非估算）：

| 指标 | 数值 |
|---|---|
| 卡片总数 / 可组卡 | 206 / 204 |
| 注册的效果键（`卡id::效果名`） | 253 个，覆盖 175 张卡 |
| 效果键 / 效果卡 平均 | 1.45 个 |
| 带随机率效果的卡 | 0（AI 决策完全确定） |
| 带 AI 钩子（aiScore/aiResponse/aiTrigger）的效果键 | 153 / 253（约 60%） |
| 效果代码总量 | 11 个文件约 1,130 行 + 30 段 `E.on` 事件接线 |
| 无效果注册的卡 | 31 张（纯白板，或如贯穿、黑魔术少女加攻等**直接硬编码在引擎里**） |

### 1.3 展示层（卡怎么显示）——全自动，零成本

- 渲染、弹窗、演出（`src/game-v2.js`、`card-view.js`）：纯数据驱动，类型/等级/阶级/Link 箭头/刻度自动识别；
- 组卡工坊（`src/workshop.js`）：自动枚举 `CARDS`，带搜索、系列筛选、分页——**新卡自动出现在牌库**；
- 卡图（`src/artwork.js`）：按 `officialName` 运行时从 YGOPRODeck API 拉取 + localStorage 缓存，断网回退占位符——**加卡不需要准备任何图片**；
- 卡组合法性校验（`src/deck-tools.js`）：40–60 主卡组 / ≤15 额外 / 同名 ≤3，全部通用逻辑。

### 1.4 构建

`scripts/build.mjs` 把所有 src 拼成**单文件** `index.html`（当前 625 KB / 204 卡 / 11 预设）。新增 src 文件要在 `scriptFiles` 数组里登记一行。

## 2. 加一张卡的真实成本（逐层拆解）

| 层 | 要写什么 | 工作量 | 可自动化？ |
|---|---|---|---|
| ① 数据行 | 1 行工厂调用 + 中文效果描述 | ⭐ 分钟级 | 可（可从卡牌数据库生成，但**中文描述没有现成免费 API**，YGOPRODeck 只有英文） |
| ② 效果实现 | `E.register/trigger/spell/trap/quick`：condition/inputs/cost/resolve；触发效果另需 `E.on` 接线 | ⭐⭐⭐⭐ 简单搜索/抽卡类 1–5 行；效果怪兽 10–20 行；复杂卡（墓地效果、每回合限制、连锁响应、特招联动）30–60 行，个别还要在 `E.op` 里写续延任务 | **否——这是主要瓶颈**，每张卡都是针对引擎 API 的定制代码 |
| ③ 引擎硬编码 | 持续性攻守计算、贯穿、多次攻击、抗性等写在 `advanced-engine.js` 里（`stat()` 内十几个按卡 id 的 if，`src/advanced-engine.js:190-209`；贯穿名单 `:1062`；`cyber-twin` 攻击次数 `:989`…） | ⭐⭐⭐ 遇到才付，且最容易漏 | 否，散落在引擎各处 |
| ④ AI 会用 | 4 处手写分数表：效果定义上的 `aiScore/aiResponse/aiTrigger`；`cardUtility` 关键卡名单（`advanced-engine.js:1177`）；召唤/额外召唤奖励表（`:1206,1214`）；目标选择愿望表（`advanced-effects.js:156-216`）+ Link 的 `linkScore` 表（`effects-link.js:90`） | ⭐⭐⭐ 不写也能玩：默认分 350，AI 会发动但**毫无 Combo 意识**（不知道先检索再展开、不知道留陷阱反制） | 否 |
| ⑤ 卡组（可选） | 预设卡组 1 行 + families 注册 1 行 | ⭐ | 可 |
| ⑥ 测试/交付 | `tests/v3-rules.test.cjs` 手写规则断言；`scripts/verify-v3-delivery.mjs` **硬编码了 `collectibleCards=204 / presetDecks=11 / rules.tests=93 / simulation=44`**——每加一批卡必炸，要同步改 | ⭐⭐ | **可（改成动态断言即可，目前是脆性设计）** |
| ⑦ 卡图 | 无（`officialName` 对上即自动） | 0 | 已自动化 |

**单卡成本区间**：白板怪 1 行 ≈ 2 分钟；简单魔陷 ≈ 10 分钟；标准效果怪 ≈ 0.5–2 小时（含 AI 分数与自测）；系列核心卡 ≈ 半天（效果 + 接线 + AI + 边缘裁定）。

**按系列批量**（推荐粒度）：一个新系列 15–25 张 ≈ 3–7 天（效果 1–2 天、AI 调教 1–2 天、规则测试 + 修 verify 计数 + 跑 AI 自对弈 1–3 天）。现有 9 个扩展系列就是这么做的。

## 3. 如果"全部"指整个现役卡池（约 1.2 万+ 张）

直说：**现有架构下不可行**，三个硬墙：

1. **效果代码墙**。175 张效果卡 ≈ 1,130 行效果代码 + 全部引擎/配套设施共 5,486 行。按此密度线性外推，1.2 万张 ≈ 数万行手写定制代码——这是**人年级**的工作量，且质量无法保证（每张卡都是并发状态机的一个分支）。参考：YGOPro 社区用"每卡一个 Lua 脚本"的方式花了十几年众包完成全卡池，每脚本仍需 30–150 行。
2. **体积墙**。当前 625 KB / 204 卡，含效果约 3 KB/卡。1.2 万张 ≈ 30–40 MB 单文件 HTML，加载与解析都成问题；单文件架构必须先拆。
3. **数据源墙**。英文数据（卡名/数值/类型）可以从 YGOPRODeck API 批量拉，但本项目卡面是**中文**且描述为手工意译，没有随取随用的中文卡数据库 API，需要接中文卡查（如 ygocdb 类数据源）并处理命名/裁定对齐。

另外规则本身也有缺口（交付报告 `output/v3-QA.md` 明确声明）：**无仪式召唤、无禁限卡表、无副卡组**；部分小众机制（接触融合、反转效果怪、连锁素材细枝裁定）未覆盖。每补一个新**机制**（如仪式）是引擎级工程，相当于 V3 加 Link 的工作量。

### 现实容量评估

| 目标规模 | 可行性 | 前提 |
|---|---|---|
| +100~300 张（精选新系列） | ✅ 顺畅 | 维持现有模式，按第 2 节清单做 |
| +500~2,000 张 | ⚠️ 吃力但可行 | 先做第 4 节的架构改造（DSL + 动态测试 + AI 默认分），代码体量到几千行后维护成本陡增 |
| 全卡池 1.2 万+ | ❌ 需要换范式 | 卡片脚本系统（类似 YGOPro Lua）或移植既有开源引擎，属于重写级项目 |

---

## 4. 建议：先做 4 件"降压力"改造，再谈大规模扩展

按投入产出排序：

1. **交付校验动态化**（半天）。把 `verify-v3-delivery.mjs` / `v3-rules.test.cjs` 里 `assert.equal(...,204)` 这类硬编码计数改为从 `CARD_LIST.length`、报告字段动态推导。现在每加一张卡都会误报"交付失败"，这是最无谓的摩擦。
2. **通用效果 DSL / 模板化**（1–2 周，收益最大）。统计现有效果，约 6–7 成是少数几个模式：检索（search）、特招（special）、破坏/除外/回手（removal）、抽弃（draw/discard）、攻守增减（modify）、无效（negate）。把这批做成声明式描述（数据里写 `effect:{pattern:'search',filter:{family:'hero'},count:1}`），引擎解释执行。新卡的常见效果从"写代码"变成"填参数"。
3. **AI 默认评分器**（2–3 天）。对没有手写钩子的卡，按效果模式给默认分（检索≈1100、清场≈1300、防御响应看 `damageThreat`…），让"没调教过的卡"至少打出及格水平。这直接把"每张卡都要写 AI 分数"从必选项降级为优化项。
4. **数据管线**（1 周）。脚本化：从英文卡牌数据库拉数值 → 合并中文译名/描述（人工校对）→ 生成 `expansion-*.js` 数据行 → 幂等重跑。让数据层的边际成本趋近于零，人力只花在效果层。

做完 1–4，单卡成本大约从"0.5–2 小时"降到"10–30 分钟"（常见卡），并且几千张规模下代码仍然可维护。

---

## 5. 附：新增一个系列的标准清单（当前模式）

1. 新建 `src/expansion-<系列>.js`（或往现有扩展文件加）：M/S/T/F/Y/X/L 定义 + `deck()` 预设 + `D.families` 注册；
2. 新建 `src/effects-<系列>.js`：效果注册 + `E.on` 事件接线 + 每个效果带 `aiScore/aiResponse`；
3. 在 `scripts/build.mjs` 的 `scriptFiles` 登记新文件；
4. 视情况往 4 处 AI 表加分数（§2④）；
5. 补 `tests/v3-rules.test.cjs` 关键裁定测试；更新 `verify-v3-delivery.mjs` 的硬编码计数；
6. `npm run build` + 跑 `v3-simulation`（AI 自对弈）确认新系列能完整打完不报错；
7. `officialName` 与 YGOPRODeck 英文名核对（否则没卡图）。
