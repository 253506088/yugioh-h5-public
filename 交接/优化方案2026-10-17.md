# 项目优化方案（2026-10-17）

本文记录 2026-10-17 提出的一轮整体优化需求、现状实测、分阶段方案与具体落地步骤。

读者对象：后续接手本项目的开发者 / 维护者 / AI 代理。

## 0. 需求原文

> 当前项目太臃肿了，战斗时的决斗盘感觉体验不好，斗蛐蛐模式很慢很卡顿，并且联机没做到 p2p 这种无服务器的模式，h5 页面也很庞大用户加载起来慢吞吞，给个优化方案吧。

拆成五条可执行的目标：

1. **项目臃肿**：仓库体积、构建产物、历史归档需要收敛。
2. **决斗盘体验差**：战斗中卡顿、交互不顺手、移动端表现差。
3. **斗蛐蛐（机器人 vs 机器人观战）慢且卡顿**：需要可调速、不阻塞界面。
4. **联机不是 P2P**：希望做到无服务器的好友联机。
5. **H5 首屏加载慢**：页面产物体积需要数量级下降。

同日追加的需求（附截图，详见第 6 节）：

6. **PC 端决斗盘的卡面太小、看着局促**——这是 PC 布局调整的核心目标（6.0），右侧栏抽屉化（6.1）与顶栏合并（6.2）都只是腾空间的手段。
7. **选中卡片要能立刻看到效果**，不能多一步"查看卡牌详情"，参考《游戏王：决斗链接》（6.3）。
8. **部分卡牌描述与效果不符，需要校准**（6.5），优先级最低。
9. **先后手不能在场外选择，必须猜拳决定**；并且重赛不能默认我方先攻（6.6）。
10. **命运轮盘2 掷骰时机缺陷**：玩家跳过主要阶段 2 直接结束回合时，也应触发那一次掷骰（6.7）。

附加约束（用户明确说明）：

- 同一时间有另一个代理在实现 2025 年度卡片，**只做增量、不改架构**。本方案不得干扰它，也不应改动它正在维护的文件。
- 本方案只做分析与规划；是否施工、按什么顺序施工由用户决定。

### 1.1 首屏加载的实际路径

当前 `scripts/build.mjs` + `scripts/lib/embedded-scripts.mjs` 的启动链路是：

1. 浏览器下载整个 `index.html`（约 86 MB）；
2. 执行内联脚本：对约 10.6 MB 的 base64 文本做 `atob`；
3. 通过 `DecompressionStream('gzip')` 解出 45.8 MB 源码文本；
4. `document.createElement('script')` + `textContent` 注入；
5. 浏览器在主线程**同步解析并执行 45.8 MB JS**；
6. 期间构建 13,526 张卡的数据对象与三语词条。

卡顿主要发生在第 2–5 步，属于数据搬运与解析成本，而非渲染成本。这也是"页面慢吞吞"的主因。

### 1.2 斗蛐蛐卡顿的根因

- `src/game-v2.js:510` 的 `runAIStep()` 在 `setTimeout` 回调里直接调用 `engine.aiNext()`；
- `engine.aiNext()` 内部会走 `src/ai-planner.js` 的推演层：`BUDGET=30`、`DEPTH=2`、`CANDIDATES=4`，每个候选还要经 `DuelAIMarginal.project` 克隆引擎做投影；
- 这些计算同步运行在 **UI 主线程**上；
- 每执行一个动作后 `dispatch → render()`，而 `render()`（`src/game-v2.js:389` 起）会整体重建双方怪兽区、魔陷区、左右侧栏、手牌、战斗日志等 DOM（全文共 24 处调用 `render()`）；
- 淘汰赛默认并发 4 场（`src/tournament.js:44`）、默认 `turbo` 节奏，等于同时有多套引擎 + 推演争抢同一根主线程；
- 主界面与决斗盘各有一个常驻 `requestAnimationFrame` 动画循环（星空 canvas、粒子），切换页面或后台时未必停止。

结论：斗蛐蛐的"慢"来自 AI 单步决策耗时，"卡"来自主线程被推演和整盘重绘同时占满。解决办法是把计算搬出主线程，并把"实时观战"改成"预计算 + 回放"。

### 1.3 决斗盘体验的具体开销点

- `backdrop-filter` 共 9 处（`src/experience.css` 6 处、`src/style.css` 3 处），移动端合成开销大；
- 战斗特效每次生成 15 个粒子 + 冲击环 + 射线（`src/game-v2.js:1017` 附近），且没有并发上限/对象池；
- 交互依赖"点卡 → 点目标 → 确认"，移动端热区与拖拽焦点不够顺手。

### 1.4 联机现状

- 现有联机是**中心服务器权威**：`server/index.mjs` 提供 WebSocket（`/pvp/ws`）与静态文件，`server/service.mjs` 负责房间、会话、双帧校验、断线计时；
- 客户端 `src/pvp-client.js` 的 `Connection` 直接依赖 WebSocket 与同源服务器；
- `src/pvp-ui.js` 与协议解耦程度尚可，主要依赖消息类型而不是传输方式；
- 因此"无服务器 P2P"是**新增一条传输通道**，不是重写现有联机。

## 2. 总体方案

按投入产出比排序，分五个阶段：

| 阶段 | 内容 | 收益 |
|---|---|---|
| 0 | 基线测量 | 让后续改动可量化验收 |
| 1 | 加载架构改造（卡图外置 + 分块加载） | 首屏 86 MB → 1 MB 级 |
| 2 | AI 移出主线程 + 观战预计算回放 | 斗蛐蛐不再卡顿，节奏可控 |
| 3 | 决斗盘渲染与特效优化 | 帧率稳定、移动端体验提升 |
| 4 | WebRTC P2P 联机（房主权威） | 无服务器好友对战 |
| 5 | 仓库与产物卫生 | 磁盘 20 GB → 数 GB |

阶段 2、3 可并行；阶段 4 独立。阶段 1 中的"卡图外置/输出格式"部分与 2025 代理的冲突面最小，可最先动。

## 3. 阶段 0：基线测量

目的：所有优化都有前后对比数字。

1. 在 `src/index.template.html` 启动脚本开头加 `performance.mark('boot-start')`，在首屏可交互、进入决斗屏时各打一个 mark，输出到 `console` 或 `report`。
2. 用 Chrome DevTools Performance / Lighthouse（移动端预设）记录一次：
   - 首屏 LCP、TBT、主线程长任务数量；
   - 进入决斗盘后的帧率与长任务；
   - 斗蛐蛐 turbo 节奏下单步决策耗时分布。
3. 把基线值写入 `docs/performance-baseline.md`，后续每阶段完成后更新。

验收：有可对比的数字表，而不是"感觉快了"。

## 4. 阶段 1：加载架构改造（最高优先级）

### 4.1 核心思路：双构建目标

不要继续把单文件构建设得更好，而是承认两种发布形态，共用同一套源码：

- `npm run build:web`（**部署默认**）：`index.html` 只作为壳，脚本、卡数据、卡图全部走独立静态文件；服务器开启压缩与长缓存。
- `npm run build:single`（**保留现有 `scripts/build.mjs`**）：继续产出单文件 `index.html`，用于离线分发，同时作为现有测试套件的 fixture。

这样现有 5,687 项检查、浏览器测试、模拟测试全部继续针对单文件包运行，不受影响。

### 4.2 具体做法

#### (1) 卡图停止内联

- `src/artwork-hybrid.js` 已经支持 URL 源、`IntersectionObserver` 懒加载和失败回退，问题只在于构建时把 `DUEL_ORIGINAL_ART` 灌成了 data URL。
- web 构建改为：`window.DUEL_ORIGINAL_ART = { '<card-id>': '/assets/duel/art/<card-id>.webp', ... }`；文件名可加内容哈希前缀或查询串，配合 `Cache-Control: public, max-age=31536000, immutable`。
- 保留 `DUEL_ART['card-back']` 单张小图内联（体积极小），避免首屏空窗。
- **预期：86 MB → 约 11 MB。**

#### (2) `.gz` 内联包改为真实文件

- web 构建不再使用 `scripts/lib/embedded-scripts.mjs` 的 base64 内联；改为 `<script type="module" src="/app/main.js">`。
- 服务器（`server/index.mjs` 或部署层）预压缩为 brotli / gzip 并设置 `Content-Encoding`，省掉 33% base64 膨胀和一次 `atob`。
- 浏览器可缓存、可流式解析。

#### (3) 数据按需切分

- `src/card-locales.js` 的 54,104 个词条按语言拆成三份（zh-CN / en / ja），启动只加载当前语言；完整描述可在卡查/图鉴打开时再拉。
- 常驻一份**轻量索引**：`id + 当前语言名称 + 年份 + 类型 + 简要数值`，约 1–2 MB，供卡组编辑、搜索、卡名显示用。
- `src/early-cards.js` 按 `releaseYear` 或系列拆成数据块；启动只加载当前对局所需年份/卡组涉及的部分。
- `src/card-catalog.js` 同样改为按需加载。
- 注意：这些文件都是**生成产物**（`scripts/import-early-cards.mjs`、`scripts/sync-locales.mjs`、`scripts/build-card-catalog.mjs` 生成），拆分逻辑应放在生成脚本里，不手改生成文件。

#### (4) 真正的分块

- 引入 esbuild 作为单一 devDependency（零配置、速度快），web 构建拆为：
  - `boot`：引擎核心 + 主界面；
  - `duel`：决斗盘与渲染；
  - `deck`：卡组编辑与卡查；
  - `tournament`：淘汰赛；
  - `pvp`：联机。
- 决斗屏用 `<link rel="modulepreload">` 预取，其余按路由 dynamic import。
- 对拼接后的 bundle 仍执行一次 `new Script(...)` 语法检查（保留单文件构建里的护栏）。

#### (5) 服务器/静态托管

- 静态资源带内容哈希文件名 + 长缓存；`index.html` 用 `no-cache` + ETag。
- 开启 brotli（优先）与 gzip（回退）。
- 卡图目录 `/assets/duel/art/` 单独设置缓存策略。

### 4.3 预期结果

| 指标 | 现状 | 目标 |
|---|---|---|
| 首屏传输 | 约 86 MB | < 1.5 MB |
| 首屏可交互（中端手机） | 数秒至十余秒 | < 1.5 s |
| 启动时同步解析 JS | 45.8 MB | < 2 MB |
| 进入决斗额外加载 | 0（已全部内联） | 1–2 MB 分块 |

### 4.4 验证

- `npm run build:single` 产物字节数不显著增加（可略有增加）；
- `npm run build:web` 产物中不存在大于约 2 MB 的单个 JS 文件；
- 现有 `npm test` 全绿；
- 浏览器测试（`tests/*-browser.cjs`）继续跑；如需针对 web 产物，新增一条轻量 smoke 测试（打开首页、进入决斗、进入卡组编辑）。

## 5. 阶段 2：斗蛐蛐去卡顿

### 5.1 把引擎与 AI 移入 Web Worker

- 新建 `src/engine-worker.js`，在 Worker 内加载与主线程相同的引擎脚本（web 构建下可直接 `import` 分块）。
- 主线程只发意图、收状态：`{ type: 'act', action } → { type: 'frame', snapshot }`。
- 已有 `engine.snapshot()` / `DuelEngine.restore()`（`server/engine.mjs` 亦在用），协议可以做得很薄。
- 观战模式下主线程完全不执行推演。

### 5.2 观战改为"先算完、再回放"

- Worker 内以最快速度将整场决斗算到结束（不渲染），回传动作序列与关键快照。
- 主线程按用户选择的节奏回放：
  - `turbo`：每动作约 120 ms；
  - `fast`：约 300 ms；
  - `normal`：约 700 ms。
- 回放用 `requestAnimationFrame` 驱动，速度只由 UI 决定，不再与 AI 计算耦合。
- 暂停/单步/跳转都只是回放游标操作，天然支持。

### 5.3 推演预算自适应

- 给 `src/ai-planner.js` 增加时间片上限：单步决策超过约 8 ms 即用当前最优候选收手。
- `casual` 难度直接下调 `BUDGET`。
- 该优化对"人 vs 机器人"同样生效。

### 5.4 渲染批量化

- 短期：把 `render()` 拆成区域级函数（怪兽区、魔陷区、侧栏、手牌、日志、HUD），每次动作只重绘变化区域；战斗日志改为增量 append。
- 中期：keyed diff —— 每个卡位维护稳定 DOM 节点，用 `transform` 做 FLIP 动画。
- 主界面/决斗盘的常驻动画在 `document.hidden`、观战暂停、`prefers-reduced-motion` 时停止。

### 5.5 验证

- 用 Performance 面板确认斗蛐蛐 turbo 下没有超过 50 ms 的长任务；
- 淘汰赛并发 4 场时界面仍可操作；
- 现有 `npm run test:tournament`、`test:ai`、`test:simulation` 全绿；
- 回放结果与直接运行的结果一致（录像/结果比对）。

## 6. 阶段 3：决斗盘体验

阶段 3 分四部分：6.0 是**核心目标**（用户 2026-10-17 明确：下面所有 PC 端调整都是为了解决"卡面太小、看着局促"）；6.1–6.3 是三条具体布局需求（附截图）；6.4 是性能与移动端专项；6.5 是卡牌文案校准；6.6–6.7 是用户追加的对局流程缺陷（先后手判定与命运轮盘2 掷骰时机）。

### 6.0 核心目标：决斗盘的卡面要变大

**需求**：用户在看完三张截图后补充说明——"上述所有对于 PC 端决斗盘的调整，都是基于感觉这里面的卡片展示的太小了，感觉看着很局促不舒服。"所以 6.1（抽屉）和 6.2（顶栏合并）**不是目的，是腾空间的手段**；真正的验收标准是**卡面尺寸显著变大**。

**现状与根因**（`src/style.css`）：

- 卡位尺寸由两个 CSS 变量控制：`:root{--zone-height:100px;--zone-width:78px}`（约第 35 行）；
- 视口断点再按"屏幕高度"缩小它们（全部是 `min-width:1081px` 的 PC 规则）：

| 断点 | `--zone-height` / `--zone-width` |
|---|---|
| `min-width:1600px` | 108px / 84px |
| `(max-height:1150px)` | **87px / 68px** |
| `(max-height:920px)` | 75px / 59px |
| `(max-height:820px)` | 62px / 48px |
| `max-width:1080px` | 96px / 74px |
| `max-width:760px` | `clamp(68px,15vw,100px)` / `clamp(49px,11vw,78px)` |

- **1920×1080 显示器恰好落在 `max-height:1150px` 档，实际卡位只有 87px 高、68px 宽**——这就是"局促"的直接原因。系统为了在一屏内放下整盘，用屏幕高度去砍卡面，而不是优先保证卡面可读；
- 此外 `.field-stack{max-width:584px}`（1600px 以上也只放到 640px），把中央牌区钉死在约 640px 宽，而 1920 屏的中央栏有 1000+ px 可用，结果两侧留白多、中间牌小；
- `.zone-row` 是 `repeat(5, minmax(0,var(--zone-width)))` + `justify-content:center`，牌区不会跟着容器变宽；
- 手牌 `.hand-slot` 在 1080p 下是 `87px` 宽（`max-height:1150px` 档），同样偏小。

**做法**：

1. **尺寸策略改为"宽度优先、高度自适应"**：`--zone-width` 用 `clamp()` 跟随视口宽度，例如 `clamp(78px, 5.4vw, 112px)`，`--zone-height: calc(var(--zone-width) * 1.28)`（保持 0.79 左右的卡面比例）。1920 宽时约 104×104 可视高，比现在的 87 高约 20%，2560 宽时接近上限 112。
2. **放宽中央牌区**：`.field-stack` 的 `max-width` 从 584/640px 提到 840–960px（1600px 以上档），`.zone-row` 允许随容器拉伸（`1fr` 上限 = `--zone-width` 的 1.1–1.2 倍）。
3. **腾出的空间优先给牌区**：6.1 收起右栏 + 6.2 合并顶栏释放的宽度与高度，全部用于放大卡位和手牌，而不是留给留白。
4. **手牌同步放大**：1080p 下 `--hand-width` 从 87px 提到约 100–104px，悬停/选中态的抬升幅度同步调整，避免重叠。
5. **低高度屏幕显式降级而非无限缩小**：`max-height:820px` 档保留紧凑模式，但设置下限（例如 `--zone-width` 不低于 64px），并在设置里提供"紧凑 / 标准 / 大卡面"三档手动覆盖，写入 `prefs`。
6. **文字可读性**：卡位变大后，卡面上的名称、攻守数值字号应随之提升；当前 `.field-stats` 等文字是固定的 7–8px，改为跟随 `--zone-width` 的 `clamp()`。

**验收**：1920×1080 下开场时，场上怪兽区卡位不小于约 100px 宽，手牌卡面不小于约 100px 宽，卡面无拉伸变形；对比改动前后截图并排确认"卡面明显变大"。此项与 6.1、6.2 一起验收。

**预估**：0.5–1 天（纯 CSS 变量与断点调整 + 一轮多分辨率走查）。

### 6.1 右侧信息栏改为可隐藏抽屉

**需求**：PC 端右侧（回合控制 / 连锁响应 / 连锁轨迹 / 决斗记录）占去约 214–236 px，希望像抽屉一样收起，把空间让给决斗盘。

**现状定位**：

- 三栏布局由 `src/style.css:6` 的 `.duel-layout{grid-template-columns:224px minmax(0,1fr) 214px}` 定义，`@media` 断点（1250 / 1080 / 760 px）各有变体；

### 6.5 卡牌文案校准（优先级最低）

**需求**：用户发现部分卡片的描述与实际效果不符（截图示例为「机壳工具 丑恶 / Qliphort Scout」），需要校准。用户明确标注：**优先级最低**，排在所有加载与布局优化之后。

**数据链路现状**：

- 运行时卡牌文案来自 `src/card-locales.js`，该文件由 `scripts/sync-locales.mjs` 生成（生成文件，禁止手改）；
- 数据源是 `data/locales/` 下固定的 ygopro-database 快照（`source-manifest.json` 记录 commit `ac5d8fb8` 与各语言 CDB 的 sha256），含 zh-CN / en-US / ja 三语；
- `sync-locales.mjs` 按 `textId` 从 CDB 取 `name` / `desc`；灵摆卡用 `splitPendulum()`（约 54–55 行）按"Pendulum Effect / 灵摆效果 / ペンデュラム効果"标记切分灵摆效果与怪兽效果；
- 因此文案问题大概率来自三类，而不是本项目手写的效果代码：
  1. 上游 CDB 本身文案过时或与现行 OCG 裁定有差异（尤其 2014 年灵摆初期卡片）；
  2. `splitPendulum()` 的切分边界在某些卡上出错，把灵摆效果混进怪兽描述或反之；
  3. 少数卡在 CDB 中缺少对应 `textId`，走了英文 `originalDescription` 兜底，导致语言错配。

**做法（校准流程，不做逐个手改）**：

1. **先建审计报告**：新增 `scripts/audit-card-texts.mjs`（只读、不写运行时文件），输出以下清单：
   - 三语缺失或回退到其他语言的卡；
   - `splitPendulum()` 切分后灵摆描述/怪兽描述为空或含明显残留标记的卡；
   - 描述文本与 `originalDescription`（英文源）严重不一致的卡（可用长度差、关键数字/效果关键词比对做启发式，不追求语义等价）；
   - 同一 `textId` 对应多张卡但描述不同（CDB 复用/错配）。
2. **分类处理**：
   - 切分错误 → 修 `splitPendulum()` 的规则并重跑 `npm run locales:sync`，用审计报告做回归；
   - 上游文案过时 → 建立一份人工覆盖表（例如 `data/locales/overrides.json`，按 `cardId + language` 记录修正文案与来源说明），由 `sync-locales.mjs` 在生成时叠加，**不要直接改 `card-locales.js`**；
   - 语言错配 → 修正兜底逻辑或补充覆盖表。
3. **卡面（卡图上的印刷文字）与运行时文案不同源**：卡图是图片，无法校准；本条只针对文本层（悬停/详情/效果弹窗里显示的文字）。如果用户指的是"卡图上的文字与效果对不上"，属于卡图素材问题，需要单独的素材替换流程，不在本条范围内。
4. **抽样验收**：覆盖用户截图中的「机壳工具 丑恶」等报告案例，再抽 20–30 张跨年份卡（含灵摆、Link、仪式）人工比对官方文本。

**注意**：该文件同时被 2025 年度卡片代理依赖（新卡文案同样出自 CDB 快照），修改 `sync-locales.mjs` 或覆盖表前需确认不与 2025 批次工作冲突；审计脚本本身只读，可先行落地。

**预估**：审计脚本 0.5 天；按报告分批修正 1–3 天（取决于问题卡数量）。

### 6.6 先后手必须猜拳决定，取消场外选择

**需求**：用户明确——"无论啥对局，不能是场外选择谁先谁后"；同时指出"认输后再来一盘默认我方先攻，这不可以的，必须猜拳决定"。

**现状定位**：

- 新建对局弹窗里有一个"出场顺序"分段控件：`src/game-v2.js:839` 的 `segment('choose-first', setupOptions.first, [[0,'我先攻'],[1,'我后攻']])`，即人机对战可以在开局前**场外指定先后手**；
- `setupOptions` 默认 `first: 0`（`src/game-v2.js:30`、`workshop.play` 第 37 行、`renderNewGame` 第 772 行），`begin-game` 直接把 `setupOptions` 传给 `startGame`；
- **重赛缺陷**：`case 'rematch'`（`src/game-v2.js:1206`）在非观战分支写死 `startGame({...base, first: 0, seed: Date.now()})`——认输/结算后再来一盘**永远我方先攻**，这就是用户说的"最操蛋的一点"；
- 与之对照：观战模式早已走猜拳（`beginSpectate` 调 `playRps`，`src/game-v2.js:650-659`），`playRps` 目前是"双方都是机器人随机出手"的观演动画，无法直接用于人机；
- 引擎侧 `src/engine.js:17` 用 `active: options.first === 0 ? 0 : 1` 决定先手，只需要调用方传入真实结果；
- 联机已经是服务端随机（`server/service.mjs:209` `first: randomInt(2)`），无需改动；
- BO3 局间"败者选择先后"是 `src/match-core.js` 的比赛内规则（`choosing-first` 阶段），属于对局内规则，**保留**，不在本次取消范围内。

**做法**：

1. **删除场外选择**：去掉 `choose-first` 分段控件与 `choose-first` 的点击分支（`src/game-v2.js:1200`），`setupOptions` 不再携带 `first`；`begin-game` 统一走猜拳。
2. **扩展 `playRps` 为通用猜拳**：
   - 人机对战：玩家点击 ✊ / ✌️ / 🖐️ 出手，AI 随机出手，平局重猜；胜者先攻；
   - 观战模式：维持双方机器人随机出手；
   - 保留现有 1.9 s 的演出（`prefers-reduced-motion` 下 0.7 s），结果回调签名不变（`callback(first)`）。
3. **重赛必走猜拳**：`rematch` 分支改为 `startGame({...base, first: playRpsResult, ...})`，与新建对局完全一致；先攻不再依赖上一局的结果。
4. **首次启动同理**：`src/game-v2.js:1309` 的首局 `startGame({... first: 0, seed: 48}, true)` 改为猜拳结果；离线恢复存档不受影响（恢复的是既有对局，不重新判定）。
5. **BO3 衔接不变**：第一局猜拳定先后，之后按官方规则由上一局败者选择；若坚持"每局都猜拳"，需修改 `match-core.js` 的 `choosing-first` 流程，属于规则决策，建议先确认。
6. **测试更新**：`tests/interaction-flow.cjs:166`、`tests/requested-ui-browser.cjs:69` 目前点击 `choose-first`，需改为等待猜拳演出并断言 `engine.state.active` 的来源；新增一条"结算后重赛的先攻由猜拳决定"的回归用例。

**验收**：任何新对局（新建、工坊开局、重赛、首局）都无法在场外指定先后手；连续重赛若干次，先攻分布符合随机；观战与联机行为不变。

**预估**：0.5–1 天。

### 6.7 命运轮盘2：跳过主要阶段 2 时也应掷骰

**需求**：用户报告——"命运轮盘2 也有 BUG，有些时候玩家不需要进入主要阶段二，而是直接结束了，那么也应该触发由主要2才执行的一次掷骰。"

**现状定位**（`src/rule-modes.js`）：

- 命运轮盘2 的掷骰由两处钩子触发：
  - `changePhase` 钩子（第 405 行）：`if(is(this,'roulette2')&&phase==='main2')` 时掷骰；
  - `settleFrame` 钩子（第 408–409 行）：当 `frame.kind==='main-open'` 且阶段为 `main1`/`main2` 且本回合阶段未掷过时掷骰，用于兜底；
- 问题在于玩家从战斗阶段**直接结束回合**（`{type:'end'}`）时：`engine.changePhase('end')` 直接调 `endTurn()`（`src/advanced-engine.js:1236`），**根本不经过 `main2`**，也不会产生 `main-open` 帧，所以两个钩子都不触发——本回合缺失了规则明确要求的"主要阶段 2 掷骰"；
- 规则文本（`src/rule-modes.js:141`）写的是"在主要阶段1和主要阶段2开始时各掷骰一次……**跳过的阶段不掷骰**"，但用户的实际意图是：主要阶段 2 作为"每回合一次的必发时机"，即使玩家跳过它、直接结束，也应当补掷这一次。这与当前文本存在冲突，需要先确认规则口径。

**做法**：

1. **先定规则口径**（二选一，建议前者）：
   - **A. 补掷**：无论是否实际进入主要阶段 2，每回合固定掷两次（主阶段 1 一次、结束阶段前一次），跳过主阶段 2 时在结束阶段补掷；
   - **B. 维持原文**：跳过不掷，只修文档与提示文案，明确"直接结束回合则不触发"。
2. 若选 A：在 `endTurn()` 的结束路径上增加钩子——在 `settleFrame` 的 `frame.kind==='end'`、`stage===0` 处（`src/advanced-engine.js:1266`）或在 `rule-modes.js` 里 `extend('endTurn', ...)`，判断 `roulette2 && 本回合 main2 未掷过` 时补一次 `queue({op:'rule-roulette'})`，并在状态里标记 `roulettePhase = turn+':end'` 防止重复；
3. 同步更新规则文案（`rule-modes.js:141` 的 detail）与 UI 提示（`rule-modes-ui.js` 的掷骰预告）；
4. **注意链式结算**：结束阶段的弃牌检查（手牌超过 6 张）与掷骰的先后顺序要明确——建议先结算掷骰，再进入弃牌检查，避免掷骰导致手牌变化后还要二次弃牌；
5. **AI 与推演兼容**：`ai-planner.js` / `ai-marginal.js` 的投影会克隆引擎，补掷逻辑必须在 clone 后仍能正确排队，且不消耗真实随机数（沿用现有 `queue`/`op` 机制即可）；
6. **测试**：新增规则模式单测——`ruleMode:'roulette2'` 下从战斗阶段直接 `{type:'end'}`，断言结束阶段前发生了一次掷骰且 `lastRoll.turn` 正确；再跑 `test:rule-modes`、`test:rule-modes:simulation` 与淘汰赛规则模式用例，确认无回归。

**预估**：确认口径 0.5 天 + 实现 0.5–1 天。

### 6.8 布局专项与小改动的顺序

6.1–6.3 只改布局与弹层，不依赖 Worker 化，可与阶段 2 并行；建议先做 6.3（收益最直接、改动集中在 `chooseCard` 与 popover），再做 6.1 抽屉，最后做 6.2 顶栏合并（涉及三处写入逻辑，回归面最大）。

## 7. 阶段 4：无服务器 P2P 联机

### 7.1 为什么不做确定性锁步

引擎存在隐藏信息（双方手牌、盖牌）且大量使用随机数（抽牌、洗牌、猜拳等）。确定性锁步需要双方持有完整状态并保证逐位一致，改造成本高、隐藏信息容易泄露。因此选择房主权威模型。

### 7.2 方案：房主权威 + WebRTC DataChannel

- **房主**在浏览器内运行现有 `DuelEngine`；对手的操作作为意图通过 DataChannel 发来；房主调用 `validatePick` 校验后执行 `act`，再把**对对手脱敏的帧**回传。
- `server/service.mjs` 中 `frame(room, seat)` 的脱敏逻辑抽取为浏览器/服务端共用的纯函数，避免两套实现分叉。
- 消息协议保持现有类型（`hello / act / frame / validate` 等）；把 `src/pvp-client.js` 的 `Connection` 抽象成 transport 接口，WebRTC 作为新实现。
- `src/pvp-ui.js` 原则上不改，只替换底层连接。

### 7.3 信令

- 真正"无服务器"：使用 offer/answer 文本（压缩为 base64 或二维码）手动互相粘贴，零基础设施。
- STUN 使用公共服务器（NAT 打洞必需，属于基础设施而非业务服务器）。
- 对称 NAT 打洞失败时，提示回退到现有服务器联机模式。

### 7.4 取舍与定位

- 房主权威意味着房主可以作弊。因此定位为**好友对战 / 娱乐局**；排位、竞技仍走现有服务器模式。
- 现有服务器联机路径保持不变，两者并存。

### 7.5 MVP 范围与预估

| 工作 | 预估 |
|---|---|
| 抽出 transport 接口 | 0.5 天 |
| WebRTC 适配层 | 0.5–1 天 |
| 信令 UI（输入框 + 复制/粘贴 + 二维码） | 0.5–1 天 |
| 脱敏帧与服务端逻辑复用 | 0.5 天 |
| 断线重连（ICE restart） | 0.5 天 |
| 测试（P2P 协议单元 + 浏览器） | 0.5 天 |
| 合计 | 2–4 天 |

## 8. 阶段 5：仓库与产物卫生

1. **历史构建归档**：
   - `output/v4-builds` 现有 237 份、约 13 GB；
   - 构建脚本每次都会新写一份，需要保留策略（例如只保留最近 5 份 + 最近一次正式发布）；
   - `output/v4-builds` 加入 `.gitignore`；若已被跟踪，`git rm -r --cached output/v4-builds`。
2. **二进制资产**：
   - `git status` 显示几乎所有 `assets/duel/art/*.webp` 都是 modified，说明图片被重新编码并已入库；
   - 建议卡图改走 Git LFS，或不再提交生成产物、只保留源图与生成脚本；
   - 完成后 `git gc --aggressive --prune=now` 可显著缩小 `.git`。
3. **确认发布路径不重复打包**：`data/`（98 MB）与 `assets/duel/art`（363 MB）是源素材，不应进入发布包。
4. **验收**：仓库体积从约 20 GB 降到数 GB，构建时间明显下降。

## 10. 与 2025 年度卡片代理的协作边界

另一代理只做增量、不改架构。为避免冲突，约定如下。

**本方案不触碰：**

- `src/effects-2025*.js`
- `src/i18n-2025.js`
- `src/year-decks.js`、`src/chronicle-decks.js`
- `scripts/prepare-year.mjs`、`scripts/collect-years.mjs`

**需要注意：**

- `scripts/build.mjs` 中的 `scriptFiles` 数组会被 2025 代理追加新文件。若阶段 1 要把文件清单抽成共享模块（例如 `scripts/lib/script-files.mjs`）供 web 构建复用，**应等 2025 提交落地后再做**，或在独立分支上完成并最后 rebase。
- 阶段 1 的"输出格式"改造（卡图外置、脚本外链、双构建目标）可以先做，不改变文件清单，冲突面很小。

**测试基座不动：**

- 单文件构建继续产出 `index.html`；
- 现有 `npm test`、浏览器测试、模拟测试继续通过，保证 2025 新卡的测试不受影响。

## 11. 风险与注意事项

| 风险 | 说明 | 对策 |
|---|---|---|
| 双构建目标分叉 | web 构建与单文件构建行为不一致 | 共用源码与文件清单；web 构建增加 smoke 测试 |
| 数据拆分破坏现有测试 | 测试可能直接 `require` 生成文件 | 拆分在生成脚本侧完成，保持原导出接口，只新增按需入口 |
| Worker 中无法直接使用部分 DOM 相关模块 | 引擎与 UI 耦合 | 先梳理 `engine` 对 DOM/`window` 的依赖，必要时注入 stub |
| P2P 房主作弊 | 房主权威固有 | 定位娱乐局，排位保持服务器模式 |
| 缓存策略错误导致更新不生效 | 长缓存 + 哈希文件名需配套 | 资源文件名带内容哈希；`index.html` 不缓存 |
| 与 2025 代理冲突 | 同时修改构建脚本 | 严格遵守第 10 节边界 |

## 12. 一句话总结

先做"卡图外置 + 分块加载"，把 86 MB 首屏压到 1 MB 级；PC 端做一组布局专项——收起右栏、合并顶栏，**把腾出的空间全部用来放大卡面**，让决斗盘不再局促，同时让选中卡片即时显示效果；对局流程上，先后手一律猜拳决定（取消场外选择，重赛也不再默认我方先攻），并修复命运轮盘2 跳过主要阶段 2 时漏掷的问题；再把 AI 与渲染从同一根主线程上拆开，斗蛐蛐从"算一步卡一下"变成可调速回放；P2P 用"房主权威 + WebRTC 手动信令"新增一条通道，不改现有服务器联机。仓库与产物卫生随时可做，成本最低；卡牌文案校准优先级最低，但只读审计脚本可以先行。
