# 游戏王卡池按年推进方案

版本：2026-09-09。总体路线从首年推进到2026年截至本方案日期；本轮执行范围为首三年：**1999、2000、2001**。

年度是发行资料与验收的边界，实际开发按卡包或20—50张新增卡片的小批次进行。每批分别交付资料、图片、效果和验证结果，最后合并年度结果。

## 1. 首年口径与检索状态

按已知发行历史，现行KONAMI《游戏王》OCG起点是**1999年**，首个补充包为 **Vol.1，1999年2月4日**。国际TCG从2002年开始；1998年的Bandai版属于另一套产品与规则，不纳入本项目OCG／TCG卡池。

这条历史信息尚未完成本轮联网复核：只读访问KONAMI公告及Vol.1资料页时，沙箱先拒绝连接；随后正常申请网络访问被自动审批服务拒绝，审批模型接口返回HTTP 404。该404来自审批代理，并非KONAMI或资料网站返回。没有取得网页内容，也没有把访问失败写成检索成功。

待复核入口：

- KONAMI OCG官网：https://www.yugioh-card.com/japan/
- KONAMI周年公告候选页：https://www.konami.com/games/corporate/en/news/release/20230203/
- Vol.1资料页：https://yugipedia.com/wiki/Vol.1

首批范围以1999—2001年OCG首发日期筛选，后续需与发行产品清单交叉核对。不能把TCG的2002年首包日期用于日本OCG，也不能将网页抓取日期当作卡片发行日期。

## 2. 收录与去重规则

总体收录正式OCG／TCG卡片。每年目录包含常规补充包、预组／入门产品、限定包、书籍和游戏附卡、活动赠卡等；仅抓常规卡包不足以覆盖全部卡片。Rush Duel、技能卡和动画自创卡使用不同规则，不在本路线内；衍生物另行记录，不编入主卡组。

区分三种身份：

| 实体 | 含义 | 去重方式 |
| --- | --- | --- |
| 卡片 | 一种可以执行效果的卡 | 稳定内部ID，关联数据库ID和可用的卡片密码 |
| 印次／收录 | 某产品、语言、地区、稀有度中的一次发行 | 产品＋卡号＋语言＋版本 |
| 卡图 | 一张明确对应卡片的原版图片 | 图片ID与实际文件SHA-256 |

同一卡多次再版保留全部收录关系，效果只实现一次。异画与勘误保留版本，不复制出多套同名卡逻辑。卡片缺少可靠发行日期时进入待核验清单，不猜年份。

总体年度归属记录首次OCG日期、首次TCG日期及两者的最早正式日期。本轮1999—2001尚无国际TCG发行，以首次OCG日期为筛选依据。已有204张卡先映射到统一身份并审计，避免重复实现；不能因为一个系列已有预设，就把该系列未来发行的卡提前算入旧年份。

YGOPRODeck可作为基础数据、首次发行日期候选和原图来源。它提供的card_sets不能直接视为完整OCG年度产品目录；产品归属须通过OCG资料另行核对。

## 3. 本轮首三年的交付范围

先写本方案，再执行以下资料与图片采集。**抓取完成与效果实装完成分别验收。** 本轮不会把抓到文字和图片的卡自动宣称为已经可对战。

| 批次 | 范围 | 交付内容 |
| --- | --- | --- |
| C0 | 公共卡片资料快照 | 原始响应、来源和时间；可从已有快照恢复 |
| C1 | 1999首次OCG发行卡 | 去重资料、原始卡图、校验结果、待核验项 |
| C2 | 2000首次OCG发行卡 | 同上，与1999重复印次分开记录 |
| C3 | 2001首次OCG发行卡 | 同上，与前两年形成累计卡池 |
| C4 | 三年产品核对 | 包／附卡目录、卡片收录关系、缺失与冲突清单 |
| C5 | 首个实装切片准备 | Vol.1准确清单、已有实现映射、机制缺口与测试用例 |

本轮图片抓取限于1999—2001筛选出的卡，不顺带下载未来年份的卡图。原始资料快照若由供应方以全量目录返回，保存作筛选证据，未来卡不会进入三年收录清单或图片下载队列。

## 4. 每一段的执行顺序

1. 冻结年度发行清单。区分新卡、再版和勘误，核对发行地区与日期。
2. 按发行日期排列产品，建立一包或20—50张新增卡的工作批次。每张卡只有一个实现任务。
3. 提前下载并校验本批原版图片，保存原始文件和来源。
4. 审计现有规则，列出本批需要的新能力。优先补通用规则，再写具体效果。
5. 实现卡片并验证代价、时点、目标失效、限制、存档及跨卡交互。
6. 生成可玩的单HTML切片和报告，完成本批验收，再推进下一批。
7. 年内所有产品和附卡核对完成后，合并年度包并封存快照。

如果某卡引用另一张已发行卡，则补齐那个依赖；如果引用的卡当时尚未发行，保留规则但不提前开放未来卡。不能为让组合成立而改写发行历史。

## 5. 规则与卡池年代分开

默认采用统一规则版本和已核对的勘误，按发行日期限制可选卡池。这样每年不必重复维护一套规则引擎。

历史卡池不等于历史赛制。例如先攻抽卡、旧版灵摆区域、旧禁限表与旧勘误若要还原，应作为独立历史规则配置追加。本路线保留现有自由构筑习惯，卡片自身限制仍执行，不自动套用某年赛事禁限表。

当前引擎仍缺仪式召唤及若干全卡池裁定能力；若首三年清单需要，必须在该批实装前补齐，不能因为已有融合／同调／超量／灵摆／Link就视为规则完整。

数据与资源使用独立清单，界面通过规则适配接口工作。先用首年1—2个批次校准当前JS引擎的实际扩卡成本；若通用规则改动明显成为主要成本，再评估成熟规则核心。按年分批能降低交付风险，但不会自动消除全卡池的总工作量。

## 6. 原图提前落地

正式离线版的图片在开发阶段处理，游玩时不再请求卡图API或第三方图片服务器。

流程：**卡片身份确认 → 解析原图地址 → 下载原始字节 → 图片解码与校验 → 本地保存 → 生成展示副本 → 编译内嵌。**

- 每张卡先保存一套可明确核对的原版卡面与裁切插画；首刷／地区异画的精确对应另用印次资料校验，不默认第一张API图片就是历史首刷。
- 按供应方规范限速，默认低并发。失败记录原因，支持重试、断点续传；不绕过拒绝访问或用占位图伪造成功。
- 校验HTTP结果、文件格式、实际解码、尺寸、文件SHA-256、卡片与图片ID；保存原始文件，展示副本单独输出。
- 原始图片按内容哈希去重，同一图片被多次引用只下载、存储和打包一次。
- 保存来源URL、获取时间、尺寸、哈希和核验状态。每个小批次生成联系表，逐张检查错图、空图和异常裁切。
- 展示副本可使用WebP和合适分辨率，保留原版画面，不重绘；原始下载文件不删除。
- localStorage里缓存的URL不算本地图片。必须有真实可解码的文件字节，才能通过离线验收。

现有构建器已经能内嵌assets/official中的图片，但该目录目前只有说明文件。后续将由资产清单驱动内嵌，正式离线包移除运行时联网回退。缺图会阻止正式包通过验收；调试占位版本须明确标为未完成。

## 7. 单HTML与体积

继续保留单HTML交付。源码、原始数据、原图、展示副本与各轮构建均保留在项目目录，成品可单独携带。

计划使用资产索引和按需创建的本地Blob URL，避免把同一图片的Base64反复复制进每个卡牌DOM。牌库使用分页／虚拟列表，避免一次解码所有图片。

体积必须以实际下载结果校准。仅作预算示例，若每卡最终展示图平均60KB：

| 卡图数（示例） | 图片原始体积 | Base64约增加至 |
| --- | --- | --- |
| 40 | 2.4MB | 3.2MB |
| 500 | 30MB | 40MB |
| 12,000 | 720MB | 960MB |

这些不是已抓到的卡数或图片大小。首批需要测量画质、启动耗时、内存和手机表现。年度版本按“截至该年累计卡池”打包，主版本保留全部已验收内容；不能把目标悄悄改为只能逐年单独玩的互不相通卡池。

## 9. 验收与进度

不使用一个“已导入”标记代替所有完成状态。分别记录：资料已获取、日期已核验、图片已落地、图片已核验、效果已实现、对局验证已通过。

每批完成条件：卡片／印次对应明确；目标卡图文件通过检查；没有未实现效果被当成可玩卡开放；关键正反例与连锁、保存恢复通过；正式成品断网运行且不发送第三方资源请求。

年度完成还要求发行产品目录闭合、附卡和再版关系处理完成、未知日期和缺图清单归零。单个数据库返回了列表，只能证明该来源的抓取完成，不能直接证明年度全部卡片齐全。

## 10. 当前阻塞与交付边界

网络请求的自动审批接口目前存在HTTP 404问题。用户已经明确要求采集三年资料并提前保存图片，无需重复询问相同偏好。应通过正常网络审批路径执行；若仍被拒绝，保存失败报告并完成本地工具与可验证工作，不把未下载图片标为成功。

本轮会保留：年度范围配置、原始响应（成功时）、规范化卡片清单、下载队列、原图与展示副本（成功时）、失败和缺失报告、可重跑命令。游戏效果实装及正式离线HTML需在资料和图片验收之后逐批推进。
