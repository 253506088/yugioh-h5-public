# 第三方 AI 组卡接入设计

对应 2026-09-21《优化需求 1》第 4 项。本文保留原始设计与数据依据；**2026-09-22 已实现**，实际入口、配置、取舍与验证命令见 [AI 卡组导入使用说明](ai-deck-import.md)。目标只有一个：用户上传文本、图片或网址，由第三方模型解析其中的卡组，再由本作把每张卡对应到当前卡池，生成一副或多副可直接进入工坊的卡组。

2026-09-22 修订：新增第 2 节，专门回答三个问题——不让模型给 ID 那映射靠什么、怎么保证 AI 组出的卡组和本作对得上、找不到的卡怎么办；第 7 节匹配规则改为用真实卡池数据验证过的"四级精确匹配 + 全库名录"，其余章节顺延编号。文中所有数字都来自 2026-09-22 对当前仓库跑的统计脚本（`output/scratch/ai-import-*.cjs|mjs`，该目录不入库）。

## 1. 目标与不做的事

| 做 | 不做（本期） |
| --- | --- |
| OpenAI 兼容协议与 Anthropic Messages 协议两种适配器 | Gemini 协议（预留接口位） |
| 自定义 API URL、令牌、模型 ID、协议 | 验证模型 ID 是否真实存在（由上游返回错误） |
| 文本、图片、网址三种输入 | 让模型改牌、补牌、评价强度 |
| 逐卡给出"已实现／未收录／需确认"的清晰结论 | 让模型直接给出本作卡片 ID（原因见第 2.1 节） |
| 一次内容产出多副卡组 | 对战中调用模型 |

核心原则：**模型只负责"读"，卡片身份由本地确定。** 模型从内容里抽出"卡名 × 数量 × 分区"，本作用三语名称与卡片密码在 6,275 张卡池里做确定性匹配。模型永远不会返回本作的内部 ID，也就不存在编造一张不存在的卡的问题。这句话具体怎么落地，见第 2 节。

## 2. 映射机制详解（答疑）

### 2.1 模型不给 ID，那映射靠什么

结论：**模型交出来的是"名字"，本作把名字换成 ID。** 这一步和查字典一样是确定性的，不需要模型知道本作的任何内部信息。

为什么坚持不让模型给 ID：

| 如果让模型给…… | 问题 |
| --- | --- |
| 本作 ID（`blue-eyes`、`early-98645731` 这类字符串） | 模型从没见过这套 ID，只能编。 |
| 卡片密码（8 位数字） | 模型"记得"常见卡的密码，冷门卡经常错一两位；错的密码往往还是**另一张真实存在的卡**，会静默换成错卡，比"找不到"更糟。 |
| 把卡池名单塞进提示词让它选 | 6,275 张卡的三语名有 18,674 个键、十万量级 token，每次请求都要带；更糟的是会诱导模型"凑"一个最像的名字，而不是承认没找到。 |

名字之所以可靠，是因为**名字印在用户给的内容里，模型只需要"抄"，不需要"回忆"**。抄写几乎不产生幻觉，回忆一定会。而且每个名字都要过本地索引这一关：抄错或编造的名字过不了精确匹配，会被标成"需确认"或"无法识别"摆在用户面前，不会悄悄进卡组。

### 2.2 索引：从哪些字段建、有多少键

数据来源全部是仓库里已有的离线数据：

| 来源 | 字段 | 说明 |
| --- | --- | --- |
| `D.CARDS[id]`（`src/cards.js`、`src/early-cards.js` 等） | `id`、`name`、`en`／`officialName`、`providerId`、`implementationStatus`、`releaseYear` | `id` 是本作内部 ID；`providerId` 就是 8 位卡片密码；导入卡（`early-*`）的 `name` 绝大多数直接是英文官方名 |
| `DuelCardLocales[id].locales`（`src/card-locales.js`，由 `scripts/sync-locales.mjs` 从 mycard ygopro-database 的三个 `.cdb` 生成） | `zh-CN.name`、`en.name`、`ja.name` | 权威三语名；图鉴和卡片详情显示的中文名就来自这里（`DuelI18n.name`） |

当前卡池的真实数字：

| 项 | 数量 |
| --- | --- |
| 可编入卡组的卡（不含衍生物） | 6,275 |
| 有密码（`providerId`） | 6,192 |
| 三语名称齐全 | 6,275（100%） |
| `implementationStatus`：implemented ／ existing ／ 无状态 | 6,084 ／ 108 ／ 83 |
| 效果待实现（pending） | 0（机制保留：以后"先采集、后实现"的年份会出现） |
| 发售年份范围 | 1999—2013 |

83 张"无状态"卡是本作早期手工自建、没有对应到供应方数据的卡（如 元素英雄 影雾女郎、废品转换者），没有密码和年份，但有三语名，能正常编入卡组。它们只能靠名字命中，密码路线找不到——第 2.4 节的全库名录顺带解决了这个问题。

**规范化分两档：**

- **轻规范化**：NFKC、小写、弯引号统一为直引号、各种连字符（‐ – — － ー）统一为 `-`、`・`／`･` 统一、连续空白合并。**保留标点。**
- **重规范化**：在轻规范化基础上去掉全部空白、标点和符号。

**分四级建四张表**，查询按 A→B→C→D 顺序，命中即停：

| 级 | 键来源 | 规范化 | 键数 | 一键多卡 |
| --- | --- | --- | --- | --- |
| A | 数据库三语名 | 轻 | 18,674 | 0 |
| B | 本作自有名（`name`、`en`、`officialName`） | 轻 | 6,592 | 0 |
| C | 数据库三语名 | 重 | 18,671 | 2（雷鸣／Raimei 与 雷-鸣／Rai-Mei） |
| D | 本作自有名 | 重 | 6,591 | 1 |

外加**密码表**：`providerId` → ID，6,192 键，无重复。

为什么分级而不是一张大表：把所有名字去标点后混在一张表里会出现 7 个"一名多卡"。原因有两类：一是本作自有名与另一张卡的数据库名撞车（自建卡 dharc-charmer 的 `name` 是"暗灵使 达克"，而这恰好是 2008 年那张 early-19327348 的数据库中文名）；二是去标点后撞车（雷鸣 与 雷-鸣）。分级之后——数据库名优先于自有名、保留标点优先于去标点——7 个冲突全部消失。

| --- | --- | --- |
| 暗灵使 达克 | dharc-charmer（Dharc the Dark Charmer, Gloomy） | early-19327348（Dharc the Dark Charmer） |

### 2.3 一张卡是怎么被解析的

```
resolve(entry)                        // entry = {name, count, language}，来自模型或结构化清单
  1. 8 位数字 → 全库名录取 alias 主号 → 密码表 → 命中返回
                                      // 密码表没有但名录有 → 用名录三语名回到第 2 步（自建卡）
  2. 轻规范化 → 表 A → 表 B           // 唯一命中返回；多命中 → ambiguous
  3. 重规范化 → 表 C → 表 D
  4. 别名表 data/card-aliases.json → 回到第 2 步
  5. 全库名录精确查（第 2.4 节）→ 命中 → not-in-pool（带官方三语名与密码）
  6. 模糊匹配（卡池 + 全库名录）→ 唯一候选且达自动阈值 → 采用并标"自动修正"
                                      → 有候选未达阈值 → ambiguous；无候选 → 7
  7.（可选，默认关）模型第二轮：请它给官方三语名 → 回到第 2 步
  8. unknown
```

前 6 步都不依赖模型，只有第 7 步会再调一次模型，而且它交回来的仍然是名字，照样要过第 2—5 步。

### 2.4 找不到的卡怎么处理：三层判定

"找不到"其实是两件不同的事：**这张卡本作没收录**，和**这串字我们认不出**。对用户来说，前者应当告诉他"这是哪张卡、为什么没有"，后者应当让他改一改再试。第一版设计把两者交给启发式判断，不够可靠；这一版用一个确定性的数据源把它们分开。

**全库名录。** 仓库里已经提交了 mycard ygopro-database 的三个语言库（`data/locales/sources/ac5d8fb8…/{zh-CN,en-US,ja-JP}.cdb`，`scripts/sync-locales.mjs` 用 `node:sqlite` 读取它们生成 `src/card-locales.js`）。这三个库覆盖**全部** 14,981 张卡（不只是本作的 6,275 张），含中英日名和 `alias`（别画、同名异号指向主号，580 行）。新增脚本 `scripts/build-card-catalog.mjs` 从中导出一份精简名录 `src/card-catalog.js`：每行 `[密码, 中文名, 英文名, 日文名, alias]`，14,981 行、约 1.3 MB（UTF-8），按现有方式随构建内联进单文件 HTML（当前 `index.html` 约 60 MB、`card-locales.js` 6.3 MB，增量约 2%）。名录只存名字，不存效果文本；建索引时按 `alias` 折叠，同名别画只算一张。

有了它，"找不到"分成三层：

| 层 | 判定 | 状态 | 用户看到的 |
| --- | --- | --- | --- |
| 1 | 名字或密码命中本作卡池 | `playable` ／ `pending` | 卡片 + 绿／黄标签 |
| 2 | 卡池没有，但全库名录有 | `not-in-pool` | 红标签；显示名录里的官方三语名与密码，一句"本作卡池目前收录 1999—2013 年 OCG 卡，这张不在其中"，附 YGOPRODeck 链接；可一键记入本地"需求清单" |
| 3 | 全库名录也没有 | 先走别名 → 模糊 →（可选）模型第二轮；仍无则 `unknown` | 灰标签；显示原文，提供输入框手动改名重试，或从模糊候选里选 |

全库名录还顺带解决三个小问题：

- **YDK 里的别画密码**：YDK 常见 89631140（青眼白龙别画），本作只有 89631139；名录里 89631140 的 `alias` 指向 89631139，先换主号再查密码表。
- **83 张无密码自建卡**：YDK 给的密码在本作密码表里查不到，但名录能把密码换成三语名，再按名字命中。
- **模型第二轮给的"官方名"可信吗**：它同样要过名录这一关。编出来的名字过不了，仍是 `unknown`，不会被当成"未收录的真卡"。

**第 3 层的模糊匹配规则**（对轻规范化后的字符串，同一文字系统内比较；子串判断用重规范化，避免空格干扰）：

- 成为候选：编辑距离 ≤ 1 且长度 ≥ 3；或编辑距离 ≤ 2 且长度 ≥ 8；或相似度（1 − 距离 ÷ 较长者长度）≥ 0.86；或一方是另一方的子串且较短者长度 ≥ 4。
- 自动采用：唯一候选，且（编辑距离 ≤ 1 且长度 ≥ 5，或相似度 ≥ 0.94）；结果页标"自动修正：原文 → 采用名"。
- 其余：`ambiguous`，下拉列出候选（最多 5 个，按相似度排序），默认不入草稿。
- 候选池同时包含卡池和全库名录，同一密码的候选合并；若最像的只在名录里，结论是 `not-in-pool`（标"模糊"），而不是勉强塞进一张卡池里长得像的卡。

中文短名特别说明：OCR 把"青眼白龙"认成"青眼白尤"时，4 字错 1 字，相似度只有 0.75，纯阈值会漏掉；"编辑距离 ≤ 1 且长度 ≥ 3"这条就是为它加的，它会成为唯一候选但不自动采用，用户点一下确认。反过来 "Pot of Dualty"（漏一个字母）距离 1、长度 14、相似度 0.93，直接自动修正为 Pot of Duality。

### 2.5 端到端示例

用户粘贴的一段帖子（节选）：


模型按第 6 节的 Schema 返回（它不知道本作有哪些卡，只是把看到的抄下来）：

```json
{"decks":[{"name":"帖子卡组",
  "main":[{"name":"强欲而谦虚之壶","count":3,"language":"zh"},
          {"name":"效果遮蒙者","count":2,"language":"zh"},
          {"name":"增殖的G","count":1,"language":"zh"},
          {"name":"灰流丽","count":2,"language":"zh"},
```

本地逐卡解析（以下每一行都用第 2.3 节的流程在当前卡池上实际跑过）：

| 原文 | 走到哪一步 | 结果 | 状态 |

### 2.6 "AI 成功组出一套卡组"由谁保证

| 环节 | 谁做 | 依据 |
| --- | --- | --- |
| 读内容、抄卡名、数数量、分区、拆多副 | 模型 | 提示词 + strict Schema |
| 认卡（名字 → ID） | 本地 | 四级索引、密码表、全库名录、别名、模糊 |
| 判可用（收录了没、效果实现了没） | 本地 | `implementationStatus`、`releaseYear` |
| 验构筑（40—60、≤15、≤3 同名、额外类型） | 本地 | `DuelDecks.analyze` |
| 组卡组、进工坊 | 本地 | `DuelDecks.clean / save` |

所以"成功"不是模型宣称的，而是本地校验通过的。模型不知道本作有哪些卡，也不需要知道；它对的只是用户给的内容。如果内容里本来就只有 37 张主卡，或者有 3 张本作没收录，结果页就如实显示"还差 3 张"或"未收录 3 张"，由用户在工坊补齐——系统不会为了凑够 40 张替用户填卡。多副卡组（如一篇文章里的冠亚军两套）在 Schema 的 `decks[]` 里各自独立，逐副解析、逐副校验。图片和网址只是"读"这一步的输入不同，后面的路径完全一样。

## 3. 总体流程

```
输入（文本 / 图片 / 网址）
   │
   ├─ ① 结构化优先：YDK、YDKe 链接、本作 JSON、"3 卡名" 行式清单 → 不调用模型
   │
   └─ ② 自由内容：文章、截图、网页 → 调用模型，按固定 JSON Schema 返回
           { decks:[ { name, main:[{name,count,language}], extra:[...], side:[...], uncertain:[...] } ] }
   │
   ▼
③ 本地解析（第 2.3 节）：密码 → 四级精确匹配 → 别名 → 全库名录 → 模糊 →（可选）模型第二轮
   │
   ▼
④ 逐卡状态：playable / pending / ambiguous / not-in-pool / unknown
   │
   ▼
⑤ 构筑校验（DuelDecks.analyze：40—60 主、≤15 额外、≤3 同名、额外类型）
   │
   ▼
⑥ 结果页：卡组卡片 + 状态标签 + 候选下拉 → 「载入工坊」生成草稿 → 用户保存
```

步骤 ① 让最常见的两种来源（YDK 文件、复制的清单）完全离线、零费用、零幻觉；步骤 ② 才用到模型。对全库名录也查不到的名字，可选做一次**第二轮小请求**：只把这几条发给模型，请它给出官方三语名，再回到步骤 ③ 重试。这一步仍不让模型碰 ID，而且它给的名字照样要过名录校验。

| --- | --- | --- | --- |
| 文本 | 直接作为消息正文，上限约 60 KB，超出截断并提示 | 支持 | 支持 |
| 图片 | 浏览器端缩放到最长边 1,568 px、JPEG 质量 0.85、≤ 4 MB，base64 发送；一次最多 4 张 | 支持 | 支持 |
| 网址 | 需要有人去取网页 | 浏览器不能跨域抓取任意站点；提示用户"粘贴网页文字或截图"，或使用服务器模式 | 服务器抓取并抽取正文（去 script/style、保留表格与列表文字），再走文本流程 |

网址通道是唯一必须依赖服务器的部分，设计上明确降级，不假装静态页面也能做到。

## 5. 协议适配器

`src/ai-provider.js`，同一份代码在浏览器和 Node 服务器复用（只依赖 `fetch`）。

### 5.1 配置项

```json
{
  "protocol": "openai" | "anthropic",
  "baseUrl": "https://api.wuanai.com",
  "apiKey": "sk-…",
  "model": "gpt-6-astra",
  "openaiEndpoint": "responses" | "chat-completions",
  "transport": "browser" | "server"
}
```

- `baseUrl` 只填到主机或带路径前缀（自动去掉末尾 `/`），路径由适配器拼接：`/v1/responses`、`/v1/chat/completions`、`/v1/messages`。
- 用户明确只要两种协议；`openaiEndpoint` 是 OpenAI 协议内部的接口形态，默认 `responses`（与需求里的示例一致），部分中转只开 Chat Completions，因此保留切换。这是一个需要确认的取舍，见第 11 节。
- `transport`：`browser` 直接从页面请求；`server` 经本项目服务器代理。静态部署下只有 `browser` 可选。

### 5.2 请求形态

| | OpenAI Responses | OpenAI Chat Completions | Anthropic Messages |
| --- | --- | --- | --- |
| 鉴权头 | `Authorization: Bearer` | 同左 | `x-api-key` + `anthropic-version: 2023-06-01` |
| 文本 | `input:[{role:'user',content:[{type:'input_text',text}]}]` | `messages:[{role:'user',content:[{type:'text',text}]}]` | `messages:[{role:'user',content:[{type:'text',text}]}]` |
| 图片 | `{type:'input_image',image_url:'data:image/jpeg;base64,…'}` | `{type:'image_url',image_url:{url:'data:…'}}` | `{type:'image',source:{type:'base64',media_type,data}}` |
| 系统提示 | `instructions` | `messages[0]` 为 `system` | 顶层 `system` |
| 结构化输出 | `text.format = {type:'json_schema', name, schema, strict:true}` | `response_format = {type:'json_schema', json_schema:{name,schema,strict:true}}` | 定义一个 `tools[0].input_schema` 为同一 Schema，`tool_choice:{type:'tool',name}` 强制调用，读取 `content[].input` |
| 读取结果 | 拼接 `output[].content[].text`（或 `output_text`） | `choices[0].message.content` | `content[]` 中 `type==='tool_use'` 的 `input` |
| 浏览器直连 | 一般允许跨域 | 同左 | 需额外头 `anthropic-dangerous-direct-browser-access: true`，中转站是否放行由其决定 |

三种形态返回同一个 JSON；解析后再用本地 Schema 校验一次，缺字段或类型不符视为失败，不把半成品塞进工坊。

### 5.3 错误与重试

- 401／403：令牌无效；404：接口路径或模型不存在（提示检查 `openaiEndpoint` 与模型 ID）；429／5xx：指数退避重试 2 次（1 s、3 s）。
- 浏览器 `TypeError: Failed to fetch` 且上游可达 → 判定为跨域被拒，提示改用服务器模式或换支持跨域的中转。
- 超时 60 s；图片过大在发送前拦截；返回 JSON 无法解析时把原文前 500 字展示给用户，便于排查中转站的包装差异。
- 「测试连接」按钮发送一次最小请求（"回复 OK"），显示往返耗时与上游返回的模型名。

## 6. 提示词与 Schema

### 6.1 第一轮：抽取清单

系统提示固定，用户内容单独一条消息，图片跟在文字后：

> 你是游戏王卡组清单抽取器。只从给定内容中抽取卡组：保留卡名原文（不要翻译、不要改写为别名），给出每张卡的数量与所在分区（主卡组／额外卡组／副卡组）。内容中有多副卡组时全部列出并各自命名。无法确定数量时填 1 并在 `uncertain` 里说明。不要补充内容里没有出现的卡，不要给出任何编号。严格按 Schema 返回 JSON。

Schema（strict）：

```json
{
  "type":"object","additionalProperties":false,
  "properties":{
    "decks":{"type":"array","items":{
      "type":"object","additionalProperties":false,
      "properties":{
        "name":{"type":"string"},
        "main":{"type":"array","items":{"$ref":"#/$defs/entry"}},
        "extra":{"type":"array","items":{"$ref":"#/$defs/entry"}},
        "side":{"type":"array","items":{"$ref":"#/$defs/entry"}},
        "uncertain":{"type":"array","items":{"type":"string"}}
      },"required":["name","main","extra","side","uncertain"]}}
  },"required":["decks"],
  "$defs":{"entry":{"type":"object","additionalProperties":false,
    "properties":{"name":{"type":"string"},"count":{"type":"integer","minimum":1,"maximum":3},"language":{"type":"string","enum":["zh","en","ja","unknown"]}},
    "required":["name","count","language"]}}
}
```

不向模型发送卡池名单：6,275 × 3 语名称远超合理上下文，而且会诱导模型"凑"名字。匹配在本地完成。

### 6.2 第二轮（可选）：认不出的字符串

只在第 2.3 节第 7 步触发，只发送仍为 `unknown` 的几条：

> 下面每一行是从一份卡组清单里抽出、但未能对上卡名的字符串。逐条判断它是不是游戏王卡名（可能是简称、俗称、错别字、OCR 错误或其他语言写法）。若是，给出该卡的官方中文名、英文名和日文名；若不是卡名，`isCard` 填 false。不要给出任何编号，不要新增或合并行。

Schema（strict）：`{ items:[ { input, isCard, zh, en, ja } ] }`，`items` 长度必须等于发送的行数。返回的三个名字逐个走第 2.3 节第 2—5 步；全库名录也查不到的，维持 `unknown` 并注明"模型也无法确认"。

## 7. 本地卡片解析器

`src/card-resolver.js`，纯函数，可单测。首次使用时从 `D.CARDS` 与 `DuelCardLocales` 建四张表和密码表（约 25,000 个键，毫秒级），从 `DuelCardCatalog` 建全库名录索引（14,981 行按 `alias` 折叠，约 43,000 个名称键）。

1. **规范化**：第 2.2 节的轻／重两档。中文简繁不转换（数据库是简体，繁体写法走别名表或模糊匹配）。
2. **四级精确匹配**：表 A→B→C→D（第 2.2 节），唯一命中即返回，多命中为 `ambiguous`。
3. **密码匹配**：8 位数字先经全库名录取 `alias` 主号，再查密码表；密码表没有但名录有的，用名录三语名回到第 2 步（覆盖 83 张无密码自建卡）；YDK 文件全部走这一步。
4. **别名表** `data/card-aliases.json`：常见简称与俗称（灰流丽、增 G、屋敷わらし、"Ash"）以及繁体写法；可增量维护。
5. **全库名录**：卡池没有但名录有 → `not-in-pool`，带上名录里的密码与三语名。
6. **模糊匹配**：第 2.4 节的规则；候选来自卡池与名录，按密码合并。
7. **第二轮规范化**（可选、默认关）：第 6.2 节。
8. 同一副卡组里重复出现的同名条目合并数量；合并后超过 3 张的按 3 张计并提示。

逐卡状态：

| 状态 | 含义 | 结果页表现 |
| --- | --- | --- |
| `playable` | 命中卡池且 `implementationStatus !== 'pending'`（含 implemented、existing 与无状态的自建卡） | 绿色，直接进入草稿 |
| `pending` | 命中卡池但效果待实现（当前 0 张） | 黄色，提示暂不能用于正式决斗（工坊校验会拒绝） |
| `ambiguous` | 精确匹配多命中、模糊匹配多候选、或唯一候选未达自动采用阈值 | 橙色，下拉选择，默认不入草稿 |
| `not-in-pool` | 卡池没有、全库名录有 | 红色，显示名录官方三语名与密码、"卡池目前收录 1999—2013 年"说明、YGOPRODeck 链接 |
| `unknown` | 卡池、名录、别名、模糊、（可选）第二轮均未命中 | 灰色，显示原文，可手动输入名字重试 |

副卡组（side）单独展示，不进入草稿；用户可把其中的卡拖到主卡组。

## 9. 服务器代理（可选）

`server/ai-proxy.mjs`，仅在 `npm start` 的服务器上启用，静态部署不存在。

- `POST /api/ai/complete`：请求体是第 5.1 节的配置（不含令牌）+ 消息；令牌由浏览器通过 `X-Duel-AI-Key` 头逐次传递，服务器**不落盘、不写日志**。也允许通过环境变量 `DUEL_AI_DEFAULT_KEY` 提供托管密钥，此时限制每 IP 每小时次数（默认 30）。
- `POST /api/ai/fetch-url`：抓取网页并返回抽取的正文文本。安全限制：只允许 `https:`；解析 DNS 后拒绝私网、回环、链路本地地址（防 SSRF）；跟随最多 3 次重定向并逐次复检；响应 ≤ 2 MB；只接受 `text/html` 与 `text/plain`；超时 15 s。
- 上游主机白名单 `DUEL_AI_UPSTREAMS`（逗号分隔，默认空表示允许任意 https 主机，但同样过私网检查）。
- CSP 的 `connect-src` 已经允许 `https:`，浏览器直连不需要改动；代理路径同源。

## 10. 存储与隐私

- 令牌保存在 `localStorage` 的 `duel-sanctuary-ai-provider-v1`，仅本设备；设置页明确提示"令牌只保存在本浏览器，任何导出、存档、决斗记录都不包含它"。
- 导出卡组 JSON、赛事档案、PVP 投影都不携带 AI 配置。
- 发送给模型的内容只有用户主动提供的文本／图片／网页正文，以及第二轮里认不出的几条字符串；不附带对局或个人数据，不附带卡池名单。
- 卡片索引与全库名录都在本地构建与查询，不联网。
- 静态部署时页面通过 CSP 允许 `connect-src https:`，用户填写的任意 https 地址都能请求；这是用户的明确选择，设置页说明这一点。

## 11. 需要确认的取舍

1. **OpenAI 接口形态**：按示例默认 Responses，同时保留 Chat Completions 切换；如果只要一种，去掉切换即可。
2. **副卡组**：只展示不入草稿（当前方案），或直接并入主卡组候补。
3. **托管密钥**：服务器部署是否提供默认密钥（涉及费用与限流），或永远要求用户自带。
4. **第二轮识别**：建议默认关闭。有了全库名录后它只对"简称、俗称、错字"有帮助，别名表能覆盖大部分；开启时多一次小请求。
5. **未收录卡**：只提示，或进一步记录到本地"需求清单"供后续年份推进参考（第 2.4 节按后者设计，可缩回前者）。
6. **全库名录的体积**：约 1.3 MB 内联进单文件 HTML（当前方案，与 `card-locales.js` 同样处理），或仅在服务器部署下按需加载；单文件部署没有按需加载的余地，只能内联。
7. **5 张自有名撞名的卡**（第 2.2 节表格）：是否把自有 `name` 改成数据库中文名。不改也不影响匹配结果，只是图鉴里显示的自有名与数据库名不一致。
